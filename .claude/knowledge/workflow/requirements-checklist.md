# 需求分析檢查清單

## Quick Reference

- 使用時機: Proposal 階段，需求分析完成前
- 檢查重點: 功能性、邊界條件、非功能性、資料、整合
- 目標: 確保需求完整、明確、可實作
- 輸出: 完整的 proposal.md，包含所有必要資訊

## 使用場景

**適用於**:
- 所有新功能開發（Backend、Frontend、Full-stack）
- 功能變更或重構
- 需求不明確時

**不適用於**:
- 簡單 Bug 修復
- 文案修改
- 樣式微調

## 核心概念

需求分析檢查清單確保在進入規格化階段前，所有必要的資訊都已收集完整。這能大幅減少後續的返工和需求變更。

**關鍵原則**:
1. **問對的問題** - 使用結構化訪談
2. **量化標準** - 避免模糊的描述
3. **考慮邊界** - 不只是 Happy Path
4. **完整記錄** - 所有決策都要文檔化

## 檢查清單

### 1. 功能性需求

#### 核心功能
- [ ] 功能的主要目標已明確定義
- [ ] 使用者故事完整（As a, I want, So that）
- [ ] 成功標準可量化且可測試
- [ ] 失敗情況已充分考慮

**範例**:
```markdown
✅ 好的需求
"作為已登入用戶，我想要對業務員進行 1-5 星評分並可選填 500 字以內的評論，
以便其他用戶參考我的使用經驗。每個用戶對每個業務員只能評分一次。"

❌ 不好的需求
"用戶可以評分"
```

#### 使用者角色
- [ ] 所有相關的使用者角色已識別
- [ ] 每個角色的權限已明確
- [ ] 角色之間的互動已定義

**必問問題**:
- 誰會使用這個功能？
- 不同角色有什麼不同的需求？
- 是否需要權限控制？

#### 功能流程
- [ ] 主要流程（Happy Path）已定義
- [ ] 替代流程已考慮
- [ ] 異常流程已處理

**必問問題**:
- 正常情況下的完整流程是什麼？
- 如果某個步驟失敗會怎樣？
- 用戶可以在哪些步驟取消操作？

### 2. 邊界條件

#### 輸入驗證
- [ ] 必填欄位已明確
- [ ] 可選欄位已明確
- [ ] 資料格式已定義（如：日期格式、電話格式）
- [ ] 資料長度限制已定義

**必問問題**:
- 如果用戶不填某個欄位會怎樣？
- 欄位的最小/最大長度是多少？
- 是否允許特殊字元？

#### 極限情況
- [ ] 空值處理（null, empty, undefined）
- [ ] 極限值（最大值、最小值）
- [ ] 超出範圍的值如何處理
- [ ] 重複資料如何處理

**範例檢查**:
```markdown
評分功能邊界條件：
- [ ] 評分為 0 或 6 時如何處理？（應該拒絕）
- [ ] 評論超過 500 字如何處理？（截斷或拒絕？）
- [ ] 同一用戶重複評分如何處理？（拒絕）
- [ ] 評分對象不存在如何處理？（404 錯誤）
```

#### 併發情況
- [ ] 多用戶同時操作的行為已定義
- [ ] 資料競爭（Race Condition）已考慮
- [ ] 鎖定機制（如需要）已定義

**必問問題**:
- 如果兩個用戶同時執行會怎樣？
- 是否需要樂觀鎖或悲觀鎖？
- 最後寫入勝出還是需要合併？

#### 錯誤恢復
- [ ] 錯誤發生時的回滾策略
- [ ] 部分失敗的處理方式
- [ ] 重試機制（如適用）

### 3. 非功能性需求

#### 效能要求
- [ ] API 回應時間要求（量化）
- [ ] 頁面載入時間要求（量化）
- [ ] 預期資料量級
- [ ] 併發用戶數預估

**必問問題**:
- 預期有多少用戶同時使用？
- 回應時間要求是多少？（< 200ms, < 500ms, < 1s?）
- 預計資料會成長到多少？

**範例**:
```markdown
✅ 好的效能要求
- API 回應時間 < 200ms (P95)
- 頁面首次渲染 < 1.5s
- 支援 1000 併發用戶
- 資料量預估 100 萬筆/年

❌ 不好的效能要求
- 要快
- 不能慢
```

#### 安全性要求
- [ ] 認證機制（JWT, Session, etc.）
- [ ] 授權策略（RBAC, ABAC, etc.）
- [ ] 敏感資料加密
- [ ] API Rate Limiting

**必問問題**:
- 誰可以存取這個功能？
- 是否需要額外的授權檢查？
- 是否涉及敏感資料？
- 是否需要防止濫用（Rate Limiting）？

#### 可訪問性要求
- [ ] WCAG 等級要求（A, AA, AAA）
- [ ] 鍵盤導航支援
- [ ] 螢幕閱讀器支援
- [ ] 顏色對比要求

**必問問題**:
- 是否需要支援無障礙功能？
- 目標 WCAG 等級是什麼？
- 是否需要支援鍵盤操作？

#### 瀏覽器/裝置兼容性
- [ ] 支援的瀏覽器版本
- [ ] 支援的裝置類型（Desktop, Tablet, Mobile）
- [ ] 響應式設計要求

**範例**:
```markdown
支援環境：
- 瀏覽器: Chrome 90+, Firefox 88+, Safari 14+, Edge 90+
- 裝置: Desktop, Tablet (768px+), Mobile (375px+)
- 響應式: 必須支援 Mobile-first 設計
```

### 4. 資料需求

#### 資料模型
- [ ] 資料實體（Entity）已識別
- [ ] 資料關係已定義
- [ ] 資料欄位已列舉
- [ ] 資料類型已明確

**必問問題**:
- 需要儲存哪些資料？
- 資料之間的關係是什麼？
- 是否有外鍵關係？

#### 資料驗證
- [ ] 每個欄位的驗證規則
- [ ] 唯一性約束
- [ ] 範圍約束
- [ ] 格式約束

**範例**:
```markdown
評分資料驗證：
- rating: integer, required, 1-5
- comment: string, optional, max 500 chars
- user_id: integer, required, exists:users
- salesperson_id: integer, required, exists:salespersons
- unique: [user_id, salesperson_id]
```

#### 資料來源
- [ ] 資料從哪裡來（用戶輸入、API、資料庫、第三方）
- [ ] 資料格式（JSON, XML, CSV, etc.）
- [ ] 資料轉換需求

#### 資料生命週期
- [ ] 資料如何建立
- [ ] 資料如何更新
- [ ] 資料如何刪除（軟刪除 vs 硬刪除）
- [ ] 資料保留政策

**必問問題**:
- 資料可以修改嗎？
- 資料可以刪除嗎？
- 刪除是軟刪除還是硬刪除？
- 資料需要保留多久？

### 5. 整合需求

#### API 整合
- [ ] API 端點已明確
- [ ] API 方法已定義（GET, POST, PUT, DELETE）
- [ ] Request/Response 格式已定義
- [ ] 認證方式已明確

**必問問題**:
- 需要呼叫哪些 API？
- API 回應格式是什麼？
- 如何處理 API 錯誤？

#### 第三方服務
- [ ] 需要整合的服務已列出
- [ ] 整合方式已定義（REST, GraphQL, SDK, etc.）
- [ ] API Key / 認證資訊管理策略
- [ ] 失敗時的 Fallback 機制

#### 資料同步
- [ ] 同步頻率（即時、批次、定時）
- [ ] 同步方向（單向、雙向）
- [ ] 衝突解決策略
- [ ] 同步失敗的處理

### 6. 使用者體驗

#### 回饋機制
- [ ] 成功時的視覺回饋
- [ ] 失敗時的錯誤訊息
- [ ] Loading 狀態顯示
- [ ] 進度指示（如適用）

**必問問題**:
- 操作成功後顯示什麼？
- 操作失敗時如何通知用戶？
- 長時間操作如何顯示進度？

#### 互動設計
- [ ] 按鈕的 Disabled 狀態
- [ ] 表單的驗證時機（即時、提交時）
- [ ] 破壞性操作的確認機制
- [ ] 預設值設定

**範例**:
```markdown
評分 UI 互動：
- [ ] 星級選擇有 Hover 效果
- [ ] 提交按鈕在未選擇星級時 Disabled
- [ ] 評論有即時字數統計（X/500）
- [ ] 提交成功顯示 Toast 通知
- [ ] 提交失敗顯示錯誤訊息並保留輸入
```

#### 空狀態/錯誤狀態
- [ ] 無資料時顯示什麼
- [ ] Loading 狀態的視覺設計
- [ ] 錯誤狀態的視覺設計
- [ ] 網路斷線的處理

## 結構化訪談流程

### 階段 1: 核心功能確認（5 分鐘）

**目標**: 理解功能的核心目的

**必問問題**:
1. 這個功能要解決什麼問題？
2. 誰會使用這個功能？
3. 預期的使用頻率？
4. 最重要的 3 個功能點是什麼？

### 階段 2: 邊界情況探索（3 分鐘）

**目標**: 發現可能的邊界問題

**必問問題**:
1. 如果用戶輸入空值會怎樣？
2. 如果資料不存在會怎樣？
3. 如果同時有多人操作會怎樣？
4. 如果操作到一半網路斷線會怎樣？

### 階段 3: 效能與安全（2 分鐘）

**目標**: 確定非功能性需求

**必問問題**:
1. 預期的資料量級？
2. 回應時間要求？
3. 是否需要權限控制？
4. 是否涉及敏感資料？

### 階段 4: 使用者體驗（2 分鐘）

**目標**: 確保良好的使用者體驗

**必問問題**:
1. 成功後的回饋？
2. 失敗時的提示？
3. Loading 狀態的顯示？
4. 是否需要確認對話框？

## 常見功能類型的檢查清單

### CRUD 功能

**Create（新增）**:
- [ ] 必填欄位定義
- [ ] 預設值設定
- [ ] 唯一性檢查
- [ ] 成功後的行為（跳轉、通知）

**Read（讀取）**:
- [ ] 列表的排序方式
- [ ] 分頁設定（每頁幾筆）
- [ ] 篩選條件
- [ ] 無資料時顯示

**Update（更新）**:
- [ ] 是部分更新還是全部更新
- [ ] 是否需要版本控制（樂觀鎖）
- [ ] 更新權限檢查
- [ ] 更新歷史記錄

**Delete（刪除）**:
- [ ] 軟刪除還是硬刪除
- [ ] 確認機制
- [ ] 級聯刪除策略
- [ ] 刪除權限檢查

### 搜尋功能

- [ ] 搜尋哪些欄位
- [ ] 模糊搜尋還是精確搜尋
- [ ] 大小寫是否敏感
- [ ] 搜尋結果排序方式
- [ ] 無結果時顯示
- [ ] 搜尋建議（Autocomplete）
- [ ] 搜尋歷史

### 表單功能

- [ ] 表單欄位列表
- [ ] 必填與可選
- [ ] 驗證規則
- [ ] 錯誤訊息
- [ ] 提交後行為
- [ ] 草稿儲存（如適用）
- [ ] 表單重置

### 檔案上傳

- [ ] 允許的檔案類型
- [ ] 檔案大小限制
- [ ] 上傳進度顯示
- [ ] 多檔案上傳
- [ ] 檔案預覽
- [ ] 上傳失敗處理
- [ ] 檔案儲存位置

## 最佳實踐

### 需求文檔撰寫

- [ ] 使用具體的數字，避免模糊的描述
  - ✅ "回應時間 < 200ms"
  - ❌ "要快"

- [ ] 使用範例說明
  - ✅ 附上 Request/Response 範例
  - ✅ 附上 UI Mockup

- [ ] 列出所有假設
  - "假設用戶已登入"
  - "假設業務員資料存在"

- [ ] 記錄決策理由
  - "採用軟刪除而非硬刪除，原因是..."

### 常見錯誤

**錯誤 1: 需求過於模糊**
```markdown
❌ "實作評分功能"
✅ "允許已登入用戶對業務員進行 1-5 星評分，
    可選填 500 字以內評論，每個用戶對每個業務員只能評分一次"
```

**錯誤 2: 忽略邊界條件**
```markdown
❌ 只考慮正常流程
✅ 考慮：空值、極限值、重複操作、併發、錯誤恢復
```

**錯誤 3: 缺少量化標準**
```markdown
❌ "要快"、"要安全"
✅ "回應時間 < 200ms"、"使用 JWT 認證 + HTTPS"
```

## 決策記錄

### 當前決策 (2026-01-13)

**建立需求檢查清單的原因**:
- 原因 1: 減少需求遺漏導致的返工（目標：從 30% 降到 5%）
- 原因 2: 確保需求明確、可測試、可量化
- 原因 3: 提供結構化訪談指引，提高需求分析效率
- 原因 4: 建立標準流程，確保品質一致性

**考慮的替代方案**:
- 方案 A (自由發揮): 沒有結構，容易遺漏
- 方案 B (過度詳細): 檢查清單太長，執行困難
